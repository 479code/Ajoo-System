## What it does
Tracks Mum's rotating contribution ("ajo"/"esusu") scheme — multiple simultaneous
batches, each with its own members, monthly amount, and collection order. A
rotation position ("slot") can be shared by two or more people (a "joint
slot") who each confirm their own share independently while still only
counting as one position in the rotation. The admin (Uthman/Mum) also shares
a monthly WhatsApp update per batch — generated by the app, reflecting real
per-person confirmation status.

## Architecture (v6 — joint/sub-payer slots + percentage progress)
The entire app — UI and data — lives inside the Google Apps Script project
attached to the user's sheet. One URL (`/exec`) is the whole live app; no
separate claude.ai page, no "Connect your sheet" step.

1. **Code.gs** — `doGet(e)` serves `Index.html` via `HtmlService`. Storage is
   split into plain, human-readable tabs instead of one JSON blob per batch:
   - `Batches`: id, name, amount, currency, startMonth, createdAt, archived
   - `Participants`: batchId, participantId, name, phone, order — one row per
     rotation *slot* (a joint slot's `name` is the auto-combined label, e.g.
     "Hajara KB & Mai Shago (Nadia)")
   - `SubPayers` (v6): batchId, participantId, subPayerId, name,
     phone, amount, order — one row per co-payer of a joint slot; a solo slot
     has no rows here
   - `Queue`: batchId, participantId, queuePosition (0 = current collector)
   - `History`: batchId, round, collectorId, collectorName, monthLabel, collectedAt
   - `HistoryPayments`: batchId, round, participantId, status — keyed by
     *payer-unit* id (a sub-payer's id for a joint slot, the slot's own id
     for a solo one), not by slot id
   - `CurrentPayments`: batchId, participantId, status — same payer-unit
     keying as HistoryPayments
   - `Config` (hidden): pinHash, payAccountNumber, payAccountName, payBankName
   `getState_`/`saveState_` reconstruct/flatten the full in-memory shape from
   these tabs; `saveState_` does a full clear-and-rewrite of each tab per
   mutation (small data volume, already serialized by `LockService`) —
   **except** `togglePayment`, which as of v6.1 uses a single-cell patch
   instead (see "Performance fix" below).
   **Automatic one-time migration**: `ensureSheets_` detects an old-format
   `Batches` sheet (8-column header ending in `data`) the first time this new
   code runs, and splits every existing batch's blob into the new tabs before
   continuing (migrated batches simply have no `SubPayers` rows, which is
   correct — the old format never had joint slots).
   **Payer-units design** (the core of joint slots): `payerUnits_(p)` returns
   whoever actually owes money for a slot — either `p.subPayers` (a joint
   slot) or `[p]` itself (a solo slot). `currentPayments`/`HistoryPayments`
   are always keyed by payer-unit id, never by the parent slot's own id, so
   the whole payments schema needed zero changes for this feature — only the
   new `SubPayers` sheet and a handful of call sites that now loop over
   `payerUnits_(p)` instead of just `p`. `buildSlot_(name, phone, subNames,
   totalAmount)` builds either kind of slot: given `subNames`, it splits
   `totalAmount` evenly across everyone (main name + co-payers) and combines
   the names into the slot's display name.
   RPC surface (via `google.script.run`): `api_getState()` (also returns
   `paymentDetails: {accountNumber, accountName, bankName}`), `api_setPin(pin)`,
   `api_verifyPin(pin)`, `api_changePin(oldPin, newPin)`,
   `api_setPaymentDetails(pin, accountNumber, accountName, bankName)`,
   `api_mutate(action, pin, payload)` — actions: createBatch (draft's
   participants may carry `subNames: string[]`), editBatch (name/amount/
   **startMonth**, v6.1 — changing startMonth also retroactively relabels
   every already-collected round, v6.2), togglePayment (payload takes
   `payerId`, the payer-unit id — `participantId` still accepted as a
   fallback for a solo slot), markCollected, addParticipant (takes an
   optional `subNames` array to add a joint slot), removeParticipant,
   moveParticipant, toggleArchive, deleteBatch (refuses — silently, no
   error — once the batch has any collected history, to protect real
   records).
2. **Index.html** — same design system, same `google.script.run` RPC pattern.
   Features:
   - **Joint/sub-payer slots**: can be created at exactly two points — while
     building a new batch (a "+ co-payer" button on each draft row opens an
     inline input to add one or more co-payer names to that row before
     creating the batch) or when adding a new member to an existing batch's
     roster (same "+ Co-payer" control in the inline add-member form).
     **Known limitation**: converting an existing solo slot into a joint one
     after the fact is not supported — remove and re-add the member as a
     joint slot instead.
   - **Independent per-payer confirmation**: in the batch's hero section, a
     joint slot renders as a dashed "shared slot" group containing one
     confirm/pending chip per co-payer (each shows their own share amount),
     instead of a single chip for the whole slot. Toggling one co-payer's
     chip doesn't affect the other's. The roster also shows a "N" people
     badge on joint slots.
   - **Percentage progress**: the hero shows a money-based progress bar for
     the *current round* — "₦X confirmed of ₦Y · Z%" — computed from actual
     payer-unit amounts (so an uneven joint split is correctly weighted), plus
     a cycle-completion percentage ("round N of M · Z% of cycle complete") in
     the hero eyebrow, the home batch cards, and the full-schedule table
     (each row now also shows its payments as "c / total (pct%)").
   - **Edit batch**: "Edit" button in batch detail — name, amount, and (v6.1)
     "First collection month" (fixes a batch whose schedule shows generic
     "Month 1, Month 2…" instead of real month names — see "Month-name fix"
     below; as of v6.2 this also fixes rounds already marked collected; as of
     v6.3 it also stops working off a corrupted value in the first place).
   - **Change PIN**: key icon next to Admin pill (unlocked only) — new PIN +
     confirmation, calls `api_changePin` directly.
   - **Payment details (Settings)**: bank icon next to Admin pill (unlocked
     only) — account number/name/bank, stored once, shared by every batch.
   - **WhatsApp share**: "Share" button in batch detail (visible to everyone,
     not just admin, since the schedule is public info anyway) opens a modal
     with a live preview, generated fresh from the ledger. Two styles,
     switchable in the modal:
     - *Decorative* — replicates the user's original hand-typed format
       exactly: `*Batch 9*` / `*January to October 2026*` / a round-progress
       line (bar-chart emoji + "3 of 4 rounds complete (75%)") / numbered
       rows `(1) January 2026` then `Name 100k` + the crown/dancer/skin-tone
       emoji tag + a check mark if confirmed. A joint slot's row splits into
       `(A)Name1 50k...` / `(B)Name2 50k...` sub-lines, matching the user's
       own real example format exactly (letter, no space, then name).
     - *Clean/formal* — no emoji, `1. January 2026 — Name — ₦100k — PAID`
       style rows (a joint row lists the slot then indents `(A) Name1 — ₦50k
       — PAID` / `(B) Name2 — ₦50k — PENDING` beneath it), `Account:`/`Name:`/
       `Bank:` footer.
     **Checkmarks reflect real per-payer confirmed status** (pulled from
     `hEntry.payments`/`b.currentPayments` by payer-unit id) instead of a
     blanket "round is in history" flag. Note the natural consequence of this:
     only the *current* round's row has live payment data to check against
     (future rows haven't started collecting yet, so they always show
     unpaid/PENDING regardless of what's been confirmed toward the current
     round's pot) — this matches the ajo model, where everyone contributes to
     whichever round is active right now, not to future rounds in advance.
     Two actions: **Share on WhatsApp** (opens `https://wa.me/?text=...`) and
     **Copy text** (clipboard, with an execCommand fallback and a
     manual-select hint if both fail).
   Polls every 25s (paused while a modal is open or an input is focused)
   plus a manual refresh button.
3. **Admin PIN** gates all writes (batch mutations, edit, PIN change, payment
   details); bootstraps on first write attempt; remembered per-browser via
   `localStorage` (`ajooAdminPin`). Two replay mechanisms after a PIN prompt:
   `UI.pendingAction` (for `api_mutate` actions, via `mutate()`) and
   `UI.pendingCustomAction` (a generic closure, via `guardedAdminAction()`,
   used by payment-details-save) — both cleared together on cancel so they
   never cross-fire.

## v6.3 changes (this update — the real root cause of the month-name bug)

**What the user saw**: after using v6.2's fix, the schedule table's one
completed round showed a raw JS date dump — "Mon Jun 01 2026 00:00:00
GMT+0100 (West Africa Time)" — instead of "June 2026", and every other round
still showed generic "Month 2", "Month 3"... The user's exact words: "i dont
need the day and time and GMT thing, Just the MONTH and for all the CIRCLES
tied to the Month."

**Root cause**: this was never really a startMonth-persistence problem — it
was the *same* Google Sheets auto-conversion behavior already found and
fixed for phone numbers/account numbers in v6.1, just hitting two different
columns. `Batches.startMonth` ("2026-06") and `History.monthLabel` ("June
2026") are both date-shaped text, and Sheets was silently turning them into
real Date values in cells with default/General formatting. Reading a
Date-valued cell back in Apps Script returns an actual JS `Date` object, and
the old code did `String(dateObject)`, which calls `Date#toString()` — hence
the ugly "Mon Jun 01... GMT+0100" text. And because `Batches.startMonth` was
corrupted the same way, `monthLabel_()`/`monthLabel()`'s `.split('-')`
parsing failed on every row (not just history), which is exactly why every
other round fell back to generic "Month N" too — one root cause explained
both symptoms in the screenshot.

**The fix**, two parts:
1. `ensurePlainTextColumns_(sheets)` (Code.gs) now also forces
   `Batches!E:E` and `History!E:E` to Plain Text format, alongside the
   existing Participants/SubPayers/Config columns from v6.1. Unlike the
   original v6.1 fix (which only ran inside a sheet's one-time creation
   block, so it never touched the user's already-existing sheet), this now
   runs against the **existing** live sheet too — tracked with a one-time
   flag in Config (`plainTextFmtV2`) so it only costs one extra check per
   request, not a repeated format call every time.
2. `readStartMonthCell_(val)` / `readMonthLabelCell_(val)` (Code.gs,
   used in `getState_`) defensively check `val instanceof Date` and, if so,
   rebuild the correct plain text ("2026-06", "June 2026") straight from the
   Date's own calendar value instead of calling `String()` on it. This means
   even a cell that's *already* corrupted right now reads back correctly —
   the fix is not just "stop it from getting worse," it also repairs display
   immediately, without the user having to re-enter anything. The very next
   time that batch is edited (`editBatch`, which does a full `saveState_()`
   rewrite), the now-Plain-Text-formatted columns permanently fix the
   underlying cells too.

This is a stronger fix than the leading-zero case from v6.1: for a phone
number or account number, the actual digits are unrecoverably gone once
Sheets drops them, so that needs a one-time manual re-entry. For a date-
shaped cell, Sheets keeps the *correct calendar value*, just wrapped as a
Date instead of text — so the original meaning is always recoverable, no
manual step needed.

Verified with 12 new automated checks that directly reproduce the
corruption (injecting real Date objects into the mock sheet cells, exactly
mimicking what the live "Batch 9" sheet has right now) and confirm: clean
recovery on read, no GMT/date-dump text anywhere, the format sweep runs
exactly once per spreadsheet (not on every request), and a subsequent
`editBatch` save permanently stores plain text again — plus the full
28-check regression suite re-run clean.

## v6.2 changes

**The gap**: v6.1 added a "First collection month" field to Edit Batch, but
`doEditBatch_` only updated `b.startMonth` going forward — it never touched
`b.history[i].monthLabel`, which gets frozen permanently the moment a round
is marked collected (`doMarkCollected_` computes it once from whatever
`startMonth` existed *at that moment*, often blank). So a batch with several
already-collected rounds kept showing "Month 1", "Month 2"... for those
rounds no matter what the user set the start month to — only new rounds
going forward would show real names. The user hit exactly this with their
real "Batch 9" and reported it directly.

**The fix**: `doEditBatch_` (Code.gs) now also loops over `b.history` and
recomputes every entry's `monthLabel` from the corrected `startMonth` and
that entry's round index (`monthLabel_(sm, idx)`) whenever a valid
`startMonth` is provided — not just future/current rounds. This relies on
the existing assumption already used everywhere else in the app: rounds
collect strictly in order, so round `idx`'s real calendar month is always
`startMonth + idx`. Saving is unaffected — `editBatch` already goes through
the full `saveState_()` rewrite (unlike the `togglePayment` fast path), so
the corrected History rows persist to the sheet normally. Editing the start
month again later (e.g. to fix a typo) simply re-relabels everything again;
leaving `startMonth` out of an edit (name/amount-only edits) leaves existing
labels untouched.

Verified with 16 automated checks reproducing the exact real-world
sequence — create a batch with no start month, collect 3 rounds (freezing
"Month 1/2/3"), then fix the start month and confirm all 3 already-collected
rounds relabel to real month names and that survives a fresh sheet
read — plus the full 28-check regression suite re-run to confirm nothing
else broke.

## v6.1 changes

**1. Forced light theme.** Removed the `@media (prefers-color-scheme: dark)`
CSS block and its dark-mode overrides entirely, and changed
`html{color-scheme:light dark;}` to `html{color-scheme:light;}`. The app now
always renders with its light background, regardless of the phone/browser's
system theme setting — verified by forcing dark-mode emulation in a headless
browser and confirming the computed background stayed the light color.

**2. Mobile-responsive layout.** Added a `@media (max-width:640px)` block
reworking the top bar, search, stat cards, batch grid (single column),
hero section and its confirm buttons (stacked, full-width), the payment chip
groups (single column), tables (tighter padding), and every modal (now docks
to the bottom of the screen like a bottom sheet, rounded top corners, scrolls
internally if tall). All text inputs are now 16px, which stops iOS Safari
from auto-zooming in when you tap a field. Verified with screenshots at a
phone-sized viewport (390×844).

**3. Performance fix — "confirming a payment feels slow".** Root cause: every
write (`api_mutate`), including the very-frequent "mark this person paid"
toggle, was reading all 7 sheets, rewriting all 7 sheets, then reading all 7
sheets again — about 21 Sheets operations to flip one checkbox. Fixed two
ways: (a) `togglePayment` now patches just the one changed cell directly
(`patchCurrentPayment_`) instead of rewriting everything; (b) the app updates
the tap instantly on screen while the save happens in the background, and
quietly reverts it if the save turns out to have failed. Confirming a payment
should now feel instant instead of laggy. Verified with 25 automated checks,
including one that proves the on-screen update happens in well under a
second even against an artificially slow server.

**4. Emoji corruption fix.** The WhatsApp share text was showing replacement
boxes (¤/�) instead of the crown/dancer, bar-chart, and check-mark emoji.
Cause: pasting emoji characters directly into the Apps Script code editor is
known to sometimes mangle them. Fixed by building every emoji at runtime from
its plain numeric Unicode code point (`String.fromCodePoint(...)`) instead of
embedding the character literally anywhere in the file — including inside
code comments, so nothing pasteable-and-mangleable remains. Verified with 34
automated checks confirming the exact emoji glyphs (not corrupted bytes) show
up in generated share text.

**5. Month-name fix (superseded by v6.3, see above).** The schedule/share
text falls back to generic "Month 1", "Month 2"… labels when a batch's
"start month" isn't set — which is what happened to the user's real "Batch
9" (created before that field was always required). The Edit Batch modal
has a "First collection month" field to fix this. v6.1's own fix turned out
to be incomplete twice over — v6.2 extended it to already-collected rounds,
and v6.3 found the actual underlying corruption that both v6.1 and v6.2 were
still just working around.

**6. Leading-zero / digit-string protection (partial).** Separately noticed
in the user's pasted data: the payment account number "0013943449" had lost
its leading zeros and become "13943449". Cause: Google Sheets automatically
converts a cell that looks like a plain number into an actual Number,
stripping leading zeros — this happens to phone numbers and account numbers
alike (and, per v6.3, to date-shaped text too). Fixed for **newly created
sheets** by forcing the relevant columns (Participants phone, SubPayers
phone, Config value) to Plain Text format at sheet-creation time
(`setNumberFormat('@')`); as of v6.3 this same protection also runs against
an **existing** live sheet (see v6.3 above), so it now covers this column
too on next load.
**Still not automatically fixable for the account number specifically** —
unlike a date, once Sheets drops a number's leading zeros the original
digits are truly gone, so there's no defensive-read trick that can recover
them (that's what made the date corruption in v6.3 different and fixable
without user action). One-time manual fix still needed on the live
spreadsheet: select the Config sheet's column B (Format > Number > Plain
text — though this is likely now redundant since v6.3's format sweep does
it automatically), then re-enter the payment account number via the app's
Payment Details (bank icon) so it saves correctly this time. This has been
communicated to the user but not yet done.

## Key decisions
- **Rotation order:** fixed at batch creation; admin lists members in collection
  order, app advances automatically on "mark collected."
- **Cycle length:** always equals slot count (N slots -> N months), where a
  joint slot still counts as exactly one slot/month.
- **Payments:** every payer unit pays every round; admin toggles
  Pending/Confirmed per payer unit (so each co-payer of a joint slot
  confirms independently).
- **Joint slots:** can only be created when adding a member (new batch or
  existing roster); the total amount for that slot splits evenly across
  everyone in it. Converting a solo slot to joint later isn't supported.
- **Adding/removing members:** only while still in the upcoming queue (keeps
  history immutable). Removed members' past payment rows are preserved.
- **Reordering:** only the upcoming queue; current collector and history are locked.
- **Editing a batch:** name, amount, and first collection month, any time.
  Changing the start month retroactively relabels every already-collected
  round's month label too (v6.2), on the assumption that rounds always
  collect in strict order (round i = startMonth + i).
- **Payment account details:** one account for every batch (not per-batch),
  set once from Settings.
- **Emoji:** always built from numeric code points at runtime, never pasted
  as literal characters anywhere in the source (including comments), to be
  immune to Apps Script editor paste-corruption.
- **Any date-shaped or digit-only text column** (phone numbers, account
  numbers, `startMonth`, `monthLabel`) gets forced to Plain Text format —
  once per spreadsheet, tracked via a Config flag so it doesn't cost a
  repeated API call — because Google Sheets will otherwise silently reinterpret
  it as a Number or Date and corrupt it. Reads of `startMonth`/`monthLabel`
  additionally defend against an already-corrupted Date value by
  reconstructing the intended text from the Date's own calendar value (v6.3)
  — this class of bug is worth checking for on any *other* digit- or
  date-shaped field added later.
- **Deleting a batch:** silently refused once it has any collected history,
  to protect real records — only a same-cycle batch with zero history can be
  deleted outright.
